# ADR-002：配置合并与治理约束

**状态：** 已接受（Accepted）
**日期：** 2026-09-29
**决策者：** 项目决策人（先生）

## 结论

> **普通配置采用分层覆盖；Governance Contract 不参与普通 Merge，而是在 Effective Configuration 生成后执行最终约束验证。**

## 上下文

`governance/` 不是普通 config。例如 `governance/stages/07B.yaml` 规定「07A 必须完成」「Object ID 必须锁定」「一次只允许一个正式对象」「禁止重新生成拆解索引」，这些属于 **Contract / Constraint**，项目配置不能随便覆盖。

否则 `project_overrides.yaml` 会慢慢变成一个可以绕开整个治理体系的万能后门。

## 决策

### 1. 普通配置的覆盖顺序（越靠后优先级越高）

```text
Built-in Defaults
        ↓
config/defaults.yaml
        ↓
config/config.yaml
        ↓
projects/<project>/project.yaml
        ↓
projects/<project>/project_overrides.yaml
        ↓
Task Runtime Overrides
        ↓
CLI Explicit Arguments
```

示例：全局 `retry.max_attempts: 2` → 项目 `3` → 命令行 `--max-attempts 4` → 最终 `4`。

### 2. Governance 不参加普通 merge

Effective Config 生成后，再依次执行：

```text
Effective Config
        ↓
Governance Validation
        ↓
Schema Validation
        ↓
Stage Contract Validation
```

即使 `project_overrides.stage_07B.allow_multiple_objects: true` merge 成功，也必须 **Gate Reject**，因为它违反 Stage 07B Hard Constraint。

### 3. 规则分三档

| 档位 | 含义 |
|---|---|
| **HARD** | 不可覆盖 |
| **PROJECT** | 项目可以覆盖 |
| **RUNTIME** | 单任务可以覆盖 |

示例映射：

| 参数 | 档位 |
|---|---|
| Object ID 唯一 | HARD |
| 07B 不重新编号 | HARD |
| 最大重试次数 | PROJECT |
| ChatGPT 对话模式 | PROJECT |
| 下载目录 | PROJECT |
| 当前 Task timeout | RUNTIME |
| debug | RUNTIME |
| dry-run | RUNTIME |

### 4. Secrets 单独处理

CDP port、browser profile、token、cookie 等不混进 Governance。使用 `.env` 或 `config/local.yaml`，并加入 `.gitignore`。

## 后果

- **正面**：治理规范不会被项目配置绕过，硬约束可机器强制；配置来源清晰可追溯。
- **负面**：需在 Config 加载器里同时实现「分层 merge」与「Governance 校验」两套逻辑（Phase A 工作量略增）。
